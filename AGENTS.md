# Clipensk — обязательные правила работы

Этот файл является точкой входа для постоянных правил работы над проектом Clipensk.

## Переход в новый чат

При подготовке перехода в новый чат необходимо **обязательно** прочитать и выполнить правило:

- [`docs/WORKFLOW_NEW_CHAT_HANDOFF.md`](docs/WORKFLOW_NEW_CHAT_HANDOFF.md)

Правило применяется всегда, когда пользователь просит подготовить переход/handoff, а также используется как эталон качества handoff-контекста.

Ключевые требования:

- handoff — операционный checkpoint, а не краткое резюме;
- внешний изменяемый source of truth имеет приоритет над старым handoff;
- перед новой записью в репозиторий нужна fresh TOCTOU-проверка актуального состояния;
- нельзя объявлять PASS/build/release/merge без подтверждающего evidence;
- completed work не следует повторять без причины;
- незавершённые и неподтверждённые вопросы должны явно оставаться `UNVERIFIED`/`NOT READY` либо иметь иной точный статус;
- handoff обязан содержать `Exact resume point` и bootstrap-инструкции для нового чата.

Если между этим кратким указателем и полным правилом есть различие, **полный текст `docs/WORKFLOW_NEW_CHAT_HANDOFF.md` имеет приоритет**.

## GitHub Actions: получение evidence при ограничениях connector

Полная обязательная policy получения GitHub Actions diagnostics находится в:

- [`docs/CI_LOG_ACCESS.md`](docs/CI_LOG_ACCESS.md)

Если между краткими правилами этого раздела и `docs/CI_LOG_ACCESS.md` есть различие, **`docs/CI_LOG_ACCESS.md` имеет приоритет**.

Ассистент явно уполномочен при необходимости выходить за пределы ранее описанной процедуры получения GitHub Actions logs, если это нужно для полноты evidence и результата разработки, при сохранении обычных project safety/scope/promotion правил. Один неработающий или неполный способ получения logs не является причиной останавливаться или переходить к догадкам.

Если для продолжения разработки нужны данные GitHub Actions (status, job/step logs, artifacts, exit code или иной CI evidence), применяется следующий порядок:

1. Сначала получить данные напрямую через доступный GitHub connector/API и использовать их как основной source of truth.
2. Если прямой job/run log недоступен или неполон, использовать детерминированные workflow artifacts и другие доступные/разрешённые GitHub или project-safe diagnostic пути согласно `docs/CI_LOG_ACCESS.md`. Предыдущая инструкция по одному конкретному способу log retrieval не считается искусственной жёсткой границей.
3. Если автоматические пути всё ещё не дают требуемый evidence, **обязательно явно запросить у пользователя недостающий log/artifact** вместо догадки. Указать точный workflow/run и, когда известны, job ID или artifact name; дать пошаговые инструкции, что скачать в GitHub Actions и загрузить в чат без изменения содержимого.
4. Пользовательский evidence сверять с известными run ID, commit SHA, job/step и другими доступными метаданными, прежде чем делать вывод или durable write.
5. Если пользователь тоже не может предоставить требуемые данные, продолжать по failure-driven плану на основе доступного репозитория, локальных artifacts и подтверждённых фактов. Неподтверждённые предположения явно помечать как hypotheses/`UNVERIFIED` и предпочитать минимальные диагностические изменения вместо speculative fixes.
6. Никогда не объявлять CI PASS, encryption evidence или закрытие gate без фактического подтверждения соответствующего run/step/artifact.

Запрос данных у пользователя — это fallback для реально блокирующего отсутствующего evidence, а не замена данным, которые можно разумно получить напрямую или через project-safe escalation.

## GitHub Actions: ограниченное ожидание

После запуска или появления длительно выполняющегося GitHub Actions run приоритет остаётся за полезной независимой работой, но при необходимости разрешено ограниченное ожидание результата.

Обязательный порядок:

1. Пока run выполняется, продолжать другие независимые и полезные задачи текущего этапа, если они существуют и не создают конфликтующий CI churn.
2. Нельзя вносить speculative fixes в код, который сейчас проверяется Actions, только ради заполнения времени; работа остаётся failure-driven.
3. Если независимых задач нет либо безопасно продолжать разработку нельзя до результата run, разрешено в текущем рабочем проходе ожидать завершение уже запущенного GitHub Actions run до **20 минут**.
4. Во время такого ожидания допустим status polling с разумным интервалом; не следует создавать частые бессодержательные проверки или новые repo writes только ради ожидания.
5. Если run не завершился в пределах 20 минут, нужно остановить активную работу, кратко подвести итоги текущего этапа, сообщить конкретный run/workflow и попросить пользователя после завершения Actions дать команду продолжать или подтвердить факт завершения.
6. На следующей команде пользователя `продолжай` первым делом fresh проверить статус ранее незавершённого GitHub Actions run и продолжить с фактического результата.
7. Если во время выполнения Actions есть полезная параллельная задача, её можно подготовить в отдельной ветке, но не продвигать в `main`, если это отменит, перезапустит или сделает текущий evidence run нерелевантным.
8. Перед переходом в режим ожидания зафиксировать точную resume point: run ID, проверяемый commit SHA, текущий gate и следующий шаг для success/failure.

Лимит ожидания до 20 минут действует как постоянное правило проекта до его явного изменения пользователем.

## Рекомендация модели и сложности для следующей задачи

После каждой завершённой задачи, а также при подведении итогов сессии, остановке работы или подготовке перехода в новый чат необходимо сообщать пользователю:

- рекомендуемую модель для следующей задачи или сессии;
- рекомендуемый уровень сложности рассуждений;
- краткое обоснование с учётом ближайшей задачи, её рисков, доступных пользователю моделей и ограничений его подписки.

Рекомендация подбирается под следующий конкретный шаг; максимальная сложность не назначается автоматически. Если следующий шаг ещё не выбран, нужно явно указать, для какой предполагаемой задачи дана рекомендация.

Окончательный выбор модели и уровня сложности всегда остаётся за пользователем. Рекомендация не является обязательным требованием, не разрешает самостоятельно переключать модель и не означает разрешения начинать следующую задачу.

Это постоянное правило проекта, действующее и в новых чатах до явного изменения пользователем.

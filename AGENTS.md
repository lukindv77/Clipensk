# Clipensk — обязательные правила работы

Этот файл является точкой входа для постоянных правил работы над проектом Clipensk.

## Переход в новый чат

При подготовке перехода в новый чат необходимо **обязательно** прочитать и выполнить правило:

- [`docs/WORKFLOW_NEW_CHAT_HANDOFF.md`](docs/WORKFLOW_NEW_CHAT_HANDOFF.md)

Правило применяется всегда, когда пользователь просит подготовить переход/handoff, а также используется как эталон качества handoff-контекста.

Ключевые требования:

- handoff — операционный checkpoint, а не краткое резюме;
- внешний изменяемый source of truth имеет приоритет над старым handoff;
- перед новой записью в репозиторий нужна fresh TOCTOU-проверка актуального состояния;
- нельзя объявлять PASS/build/release/merge без подтверждающего evidence;
- completed work не следует повторять без причины;
- незавершённые и неподтверждённые вопросы должны явно оставаться `UNVERIFIED`/`NOT READY` либо иметь иной точный статус;
- handoff обязан содержать `Exact resume point` и bootstrap-инструкции для нового чата.

Если между этим кратким указателем и полным правилом есть различие, **полный текст `docs/WORKFLOW_NEW_CHAT_HANDOFF.md` имеет приоритет**.

## GitHub Actions: получение evidence при ограничениях connector

Если для продолжения разработки нужны данные GitHub Actions (status, job/step logs, artifacts, exit code или иной CI evidence), применяется следующий порядок:

1. Сначала получить данные напрямую через доступный GitHub connector/API и использовать их как основной source of truth.
2. Если connector не возвращает нужные данные, возвращает их неполно или его ограничение заметно тормозит диагностику, **не переходить сразу к догадкам**. Запросить у пользователя недостающий evidence и дать точные пошаговые инструкции: какой run/job открыть, какой artifact/log скачать или какие конкретные строки/скриншоты предоставить.
3. Пользовательский evidence сверять с известными run ID, commit SHA, job/step и другими доступными метаданными, прежде чем делать вывод или durable write.
4. Если пользователь тоже не может предоставить требуемые данные, продолжать по failure-driven плану на основе доступного репозитория, локальных artifacts и подтверждённых фактов. Неподтверждённые предположения явно помечать как hypotheses/`UNVERIFIED` и предпочитать минимальные диагностические изменения вместо speculative fixes.
5. Никогда не объявлять CI PASS, encryption evidence или закрытие gate без фактического подтверждения соответствующего run/step/artifact.

Запрос данных у пользователя — это fallback для реально блокирующего отсутствующего evidence, а не замена данным, которые можно разумно получить напрямую.

## GitHub Actions: запрет пустого ожидания

После запуска или появления длительно выполняющегося GitHub Actions run нельзя расходовать рабочее время только на повторные проверки его статуса.

Обязательный порядок:

1. Пока run выполняется, продолжать другие независимые и полезные задачи текущего этапа, если они существуют и не создают конфликтующий CI churn.
2. Нельзя вносить speculative fixes в код, который сейчас проверяется Actions, только ради заполнения времени; работа остаётся failure-driven.
3. Если независимых задач нет, либо безопасно продолжать разработку нельзя до результата run, нужно остановить активную работу, кратко подвести итоги текущего этапа и сообщить пользователю конкретный run/workflow, завершения которого требуется дождаться.
4. В такой ситуации попросить пользователя после завершения Actions дать команду продолжать или подтвердить факт завершения. Не выполнять пустой polling в ожидании.
5. На следующей команде пользователя `продолжай` первым делом fresh проверить статус ранее незавершённого GitHub Actions run и продолжить с фактического результата.
6. Если во время выполнения Actions есть полезная параллельная задача, её можно подготовить в отдельной ветке, но не продвигать в `main`, если это отменит, перезапустит или сделает текущий evidence run нерелевантным.
7. Перед переходом в режим ожидания зафиксировать точную resume point: run ID, проверяемый commit SHA, текущий gate и следующий шаг для success/failure.

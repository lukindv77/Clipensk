# Требования проекта Clipensk

## 1. Назначение

Clipensk — резидентное Windows-приложение для журналирования буфера обмена, долговременного хранения истории и быстрого повторного использования ранее скопированных данных.

Пользователь должен иметь возможность работать как со всей историей, так и с историей в контексте приложения-источника и приложения, из которого был вызван журнал.

## 2. Платформа и интерфейс

- Windows desktop.
- UI: WinUI 3 / Windows App SDK.
- Приложение работает резидентно в пользовательской сессии Windows.
- Windows Service для основного резидентного ядра не используется.
- Основной интерфейс приложения — русский.
- Архитектура должна поддерживать внешние файлы переводов других языков.
- Файлы локализации можно загрузить через настройки либо поместить в специальную папку Languages.
- При отсутствии перевода используется встроенная русская строка.

## 3. Состояние блокировки

- Все базы с фактическими данными журнала зашифрованы.
- Пользователь вводит пароль при запуске приложения.
- До успешного ввода пароля журналирование не выполняется и история недоступна.
- Пароль нигде не сохраняется: ни в БД, ни в настройках, ни в логах, ни в реестре, ни в системных хранилищах для автоматической разблокировки.
- В окне ввода пароля показывается пользовательский комментарий-подсказка к паролю. Сам пароль или существенная его часть в подсказке хранить не рекомендуется.
- Автоматическая блокировка — опция, по умолчанию отключена.
- В заблокированном состоянии доступны только настройки и обслуживание, не требующие доступа к фактическим сохранённым данным clipboard.

## 4. Базы данных

Минимально используются:

- актуальная БД `current.db`;
- служебный каталог `storage-catalog.db`;
- одна или более архивных БД `archive_*.db`.

### 4.1. Актуальная база

- Постоянно дополняется новыми событиями clipboard.
- Хранится в отдельной папке вместе с `storage-catalog.db`.
- Используется для актуальной части журнала.

### 4.2. Архивные базы

- Все архивные БД хранятся вместе в отдельной папке Archive.
- В обычной работе открываются только на чтение.
- На запись открываются только при операциях обслуживания, переноса, очистки, разделения, миграции или восстановления.
- Архив может состоять из множества физических файлов.
- Ротация архивов настраивается по количеству записей, размеру и/или охватываемому периоду дней.
- Порог размера или количества не может приводить к разделению одного календарного дня между архивами.

## 5. Периоды архивов

- Архивные базы владеют целыми календарными днями.
- Две архивные базы не должны содержать записи одного и того же календарного дня.
- Границы архива логически задаются как календарные даты.
- Внутри системы рекомендуется использовать полуоткрытый интервал `[начало дня; начало следующего дня)`.
- При обнаружении пересечения данные конфликтующего дня должны быть целиком перенесены в один архив.
- Для каждого архива хранится назначенный период покрытия, который не должен автоматически сужаться только из-за очистки записей.

## 6. Разделение архива

Должна существовать отдельная операция «Разделить архив».

Пример:

- исходный файл: `archive_000025.db`;
- при разделении на три сегмента создаются:
  - `archive_000025.db`;
  - `archive_000025_0001.db`;
  - `archive_000025_0002.db`.

При дальнейших разделениях новые файлы этого семейства получают следующий свободный инкрементальный суффикс. Вложенные имена вида `archive_000025_0002_0001.db` не используются.

Разделение возможно только по календарным датам.

## 7. storage-catalog.db

- Каталог является ускоряющим индексом и картой физического хранилища.
- Каталог должен актуализироваться при любых операциях обслуживания, меняющих данные, периоды, состав или состояние архивов.
- Потеря `storage-catalog.db` не должна препятствовать восстановлению системы.
- Каталог должен гарантированно перестраиваться по `current.db` и всем найденным архивным БД.
- Критически необходимая информация не должна существовать только в каталоге.
- Каждая БД должна быть самоописываемой и содержать собственную идентичность, роль, версию схемы и для архива назначенный период.

## 8. Журнал и период запроса

- В настройках задаётся период журнала по умолчанию.
- При открытии журнала отображается именно этот период.
- Поиск ограничивается текущим периодом до обращения к физическим БД.
- По текущему периоду определяются только необходимые архивные сегменты.
- При изменении периода пользователем текущий запрос отменяется, план чтения пересчитывается, журнал перечитывается по соответствующим базам.
- Архивные БД вне требуемого периода не должны открываться без необходимости.
- Для пользователя Current + Archive представляют единый журнал.
- При временном дублировании одной записи в Current и Archive пользователь должен видеть её один раз с признаком физического расположения.

## 9. Перенос Current → Archive

- Допускается временное дублирование одной логической записи в Current и Archive.
- Сначала данные записываются в Archive, затем проверяются, и только после подтверждения удаляются из Current.
- Состояние, при котором запись отсутствует и в Current, и в Archive, недопустимо.
- Перенос может запускаться по расписанию и вручную.
- Перенос выполняется пакетами и должен быть возобновляемым после аварийного завершения.

## 10. Обслуживание

Должны поддерживаться как минимум:

- перенос в архив;
- разделение архива;
- проверка БД;
- проверка согласованности каталога;
- очистка по условиям;
- уплотнение/VACUUM;
- оптимизация;
- миграция схемы;
- восстановление `storage-catalog.db`;
- восстановление незавершённых операций обслуживания.

Для массовых операций пользователь должен указывать:

- период дат;
- и/или явный список архивных БД.

При выборе архивной БД обязательно показывается её календарный период.

Если заданы и период, и список БД, операция применяется к пересечению этих ограничений.

## 11. Размещение данных

После выбора корневой папки рекомендуется структура:

```text
<DataRoot>\
  Current\
    current.db
    storage-catalog.db
  Archive\
    archive_*.db
  Files\
  Trash\
  Languages\
```

- Папка Current и папка Archive настраиваются отдельно.
- Папки можно изменить через настройки.
- При изменении пути соответствующие БД должны быть физически перенесены с проверкой успешности переноса.
- Для MSIX при первом запуске пользователь обязан выбрать папку хранения данных до создания БД и запуска журналирования.

## 12. Шифрование

- Все БД с историей и `storage-catalog.db` используют один MasterKey.
- MasterKey выводится из введённого пользователем пароля.
- Базовый кандидат для KDF: Argon2id.
- Базовый кандидат для шифрования SQLite: SQLCipher.
- Точные параметры криптографической схемы фиксируются отдельным архитектурным решением.

## 13. Что хранится непосредственно в БД

Конечный принцип:

> Фактический clipboard-payload, сохраняемый непосредственно в БД, должен быть текстовым и доступным для поиска. Служебные идентификаторы, даты, числовые поля и связи являются техническими метаданными и не относятся к этому ограничению.

В БД хранятся, согласно политикам и лимитам:

- Unicode/plain text;
- HTML — только в БД;
- RTF — только в БД;
- текстовые URL и другие поддерживаемые строковые представления;
- сведения о выбранных реальных файлах из `CF_HDROP`: пути, имена и данные операции, но не содержимое файлов;
- метаданные и ссылки на внешние бинарные payload.

RTF и HTML хранятся в исходном текстовом представлении и должны иметь пригодное для поиска текстовое представление.

Если формат отключён или превышает лимит размера, факт его отклонения в записи журнала не сохраняется.

## 14. Внешние файлы

В виде отдельных незашифрованных файлов сохраняются только:

- изображения из clipboard;
- разрешённые пользователем registered/private бинарные форматы приложений.

Для физической уникальности используется:

`SHA-256(точные сохранённые байты)`.

Файл сохраняется только один раз. Первоначальное размещение выполняется в подпапке даты первого сохранения:

```text
Files\YYYY-MM-DD\<SHA256>.<ext>
```

Изображения и пользовательские бинарные payload во внешнем файловом хранилище не защищаются паролем БД и доступны как обычные файлы файловой системы.

## 15. Trash внешних файлов

- Когда на внешний файл больше не остаётся допустимых ссылок, он перемещается в Trash.
- Trash организуется по датам удаления.
- Срок хранения в Trash задаётся в настройках.
- Значение по умолчанию: 30 дней.
- После истечения срока файл удаляется автоматически.

## 16. Форматы, которые не сохраняются

Не сохраняются ни в БД, ни отдельными файлами:

- `CF_WAVE`;
- `CF_RIFF`;
- Virtual file contents (`CFSTR_FILECONTENTS` и аналогичные данные виртуальных файлов).

При копировании реальных файлов через Проводник/`CF_HDROP` их физическое содержимое не копируется в Clipensk.

## 17. Неизвестные registered/private форматы

Если приложение впервые публикует неизвестный registered/private формат:

- его имя может быть зафиксировано в справочнике обнаруженных форматов данного приложения;
- binary payload по умолчанию не сохраняется;
- факт отклонения не создаёт отдельной записи в журнале;
- пользователь может впоследствии разрешить сохранение этого формата для конкретного приложения.

## 18. Политики сбора

Должны существовать:

- глобальная политика форматов;
- индивидуальная политика приложения.

Для приложения должны настраиваться:

- полное включение/отключение журналирования;
- разрешённые форматы;
- ограничения размера;
- другие ограничения конкретного формата.

По мере работы Clipensk формирует список обнаруженных приложений и их форматов.

Если параметр сбора отключается:

- соответствующие актуальные DB-данные удаляются из Current;
- DB-данные, уже находящиеся только в Archive, по общему правилу не удаляются;
- для внешних файловых форматов правило строже: соответствующие ссылки удаляются и из Current, и из Archive; архивы временно открываются на запись как операция обслуживания;
- внешний файл перемещается в Trash только если после очистки на него не осталось допустимых ссылок.

## 19. Файлы из Проводника

Для `CF_HDROP` хранится информация о файловой операции, а не копия файлов.

Базовые поля:

- полный путь;
- имя файла;
- расширение;
- является ли объект каталогом;
- порядок элемента;
- предпочтительное действие: Copy / Move / Link / Unknown.

Предпочтительное действие не следует трактовать как гарантированно выполненную файловую операцию.

## 20. Локализация

- Русский язык встроен и является fallback.
- Дополнительные языки подключаются внешними файлами.
- Внутренние идентификаторы, состояния, ключи и данные БД не локализуются.
- Через настройки должны быть доступны загрузка файла перевода, открытие папки Languages и перечитывание переводов.

## 21. Лицензирование

Clipensk должен быть полностью Open Source.

Конкретная лицензия пока не выбрана и будет зафиксирована отдельно.

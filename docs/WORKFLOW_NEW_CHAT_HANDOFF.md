# Правило формирования перехода в новый чат

Когда пользователь просит подготовить переход в новый чат, сформируй **самодостаточный handoff-контекст**, позволяющий новому чату продолжить работу без повторного исследования уже установленных фактов и без потери текущего состояния проекта.

## 1. Цель перехода

Переход должен позволить новому чату:

- понять, над каким проектом ведётся работа;
- восстановить текущую задачу и её границы;
- определить authoritative source of truth;
- знать, что уже исследовано, реализовано и проверено;
- знать, что осталось сделать;
- понимать принятые архитектурные решения и причины их выбора;
- не повторять завершённую работу;
- не считать предположения доказанными фактами;
- продолжить работу с точной последней подтверждённой точки;
- сохранить все ограничения, запреты, release-правила и требования пользователя.

Переход — это **операционный checkpoint**, а не обычное краткое резюме разговора.

---

## 2. Когда формировать переход

Формируй handoff:

- по прямой команде пользователя;
- перед переходом в новый чат;
- когда текущий чат становится очень длинным;
- после крупного исследовательского или implementation tranche;
- перед сложным этапом, если потеря контекста может привести к повторной работе;
- после создания важной ветки, commit, PR, release checkpoint или другого durable состояния.

Не переключай пользователя в новый чат автоматически. Только подготовь контекст перехода.

---

## 3. Источники истины

В handoff обязательно разделяй:

1. **Authoritative current state** — подтверждённое состояние репозитория, файлов, подключённых сервисов или других первичных источников.
2. **Durable project checkpoints** — commits, branches, PR, issues, документы, тестовые evidence и другие сохранённые результаты.
3. **Conversation-derived conclusions** — архитектурные решения и выводы текущего чата.
4. **Unverified assumptions** — всё, что ещё не подтверждено.

Если существует репозиторий, база данных, issue tracker или другой внешний source of truth, он имеет приоритет над старым текстовым handoff.

Новый чат должен **сначала проверить свежесть изменяемого внешнего состояния**, прежде чем выполнять новые записи.

---

## 4. Обязательная структура handoff

Сформируй переход со следующими разделами.

### A. Project identity

Укажи:

- название проекта;
- репозиторий / workspace / основной источник данных;
- основную ветку;
- важные пути, документы или компоненты;
- текущую версию продукта, если она существует.

### B. User intent

Кратко зафиксируй:

- конечную цель пользователя;
- текущую непосредственную задачу;
- требования к стилю работы;
- важные постоянные предпочтения;
- что пользователь явно запрещал или просил не делать.

Не включай лишние персональные данные.

### C. Current authoritative state

Укажи только подтверждённые факты:

- exact branch;
- exact commit/head;
- открытые PR/issues;
- статус тестов;
- статус build/release;
- состояние workspace;
- другие важные current-state значения.

Если exact state не был недавно перепроверен, явно напиши:

`Нужна fresh TOCTOU-проверка перед следующей записью.`

Не выдавай ожидаемый SHA или предполагаемое состояние за подтверждённое.

### D. Current owner / active task

Опиши:

- конкретную текущую проблему;
- её root cause;
- acceptance criteria;
- границы задачи;
- соседние задачи, которые не должны быть случайно объявлены закрытыми.

### E. What has been completed

Перечисли завершённые действия:

- исследования;
- решения;
- код;
- тесты;
- документы;
- commits;
- ветки;
- evidence;
- внешние проверки.

Для каждого важного durable результата по возможности указывай exact identifier.

### F. Current conclusions

Зафиксируй актуальные архитектурные и продуктовые решения.

Для каждого существенного решения желательно указывать:

- выбранный вариант;
- почему он выбран;
- какие альтернативы были отвергнуты;
- какие ограничения сохраняются;
- какие более ранние выводы были superseded.

Не оставляй в handoff противоречащие друг другу решения без пояснения, какое из них актуально.

### G. Important invariants

Отдельно перечисли правила, которые следующий чат не должен нарушать.

Например:

- атомарность;
- generation fencing;
- fail-closed behavior;
- capacity limits;
- privacy constraints;
- migration compatibility;
- release policy;
- ownership boundaries.

Этот раздел должен быть достаточно точным, чтобы следующий чат не восстановил ошибочную старую архитектуру.

### H. Known risks and unresolved questions

Перечисли:

- обнаруженные race conditions;
- незакрытые edge cases;
- зависимости;
- ограничения среды;
- неподтверждённые предположения;
- места, требующие дополнительного исследования.

Не маскируй незавершённые вопросы под completed work.

### I. Remaining work

Сформируй приоритетный список следующих действий.

Лучший формат:

1. ближайший конкретный шаг;
2. следующий логический tranche;
3. необходимые тесты;
4. документация/status updates;
5. delivery/PR/release steps.

Отделяй обязательное от желательного.

### J. Exact resume point

В конце обязательно сформулируй:

`Следующий чат должен начать с: ...`

Это должна быть одна конкретная рабочая точка, а не общее описание проекта.

Например:

`Следующий чат должен начать с fresh проверки head рабочей ветки, затем исследовать stale-cleanup snapshot→delete race. Production runtime до этого не менять.`

### K. First-turn bootstrap instructions

Добавь инструкции новому чату:

- не доверять handoff вместо свежего source-of-truth там, где состояние могло измениться;
- не повторять уже выполненное исследование без причины;
- сначала проверить current branch/head/status;
- прочитать перечисленные authoritative документы;
- использовать текущий owner и acceptance criteria;
- продолжить с Exact resume point;
- при обнаружении противоречия между handoff и текущим source-of-truth считать source-of-truth приоритетным;
- исправить handoff-derived assumption, а не пытаться подгонять repository state под старое описание.

---

## 5. Обязательные правила качества

Handoff должен быть:

- самодостаточным;
- конкретным;
- достаточно подробным для продолжения работы;
- без ненужной истории разговора;
- без скрытой цепочки рассуждений;
- без повторения уже неактуальных решений как текущих;
- без неподтверждённых заявлений о PASS, build, release или merge;
- без фраз вроде «вероятно всё готово», если отсутствует evidence;
- с exact identifiers там, где они важны;
- с абсолютными датами для важных временных checkpoint;
- с явным различием `DONE`, `ACTIVE`, `RED`, `NOT READY`, `UNVERIFIED` и аналогичных состояний.

Если какой-либо факт неизвестен, пиши `не подтверждено`, а не угадывай.

---

## 6. Работа с длинной историей

Не пытайся переносить весь чат.

Сохраняй только информацию, которая materially влияет на продолжение работы:

- требования;
- состояние;
- решения;
- evidence;
- ошибки;
- зависимости;
- remaining work;
- resume point.

Исторические детали сохраняй только если они объясняют действующий invariant или предотвращают повтор уже отвергнутого решения.

---

## 7. Durable checkpoint перед переходом

Если у проекта есть writable source of truth и пользователь разрешил записи, перед окончательным handoff желательно сохранить важные незавершённые результаты в durable форме:

- commit;
- branch;
- research/evidence document;
- issue/PR note;
- другой штатный project checkpoint.

Не создавай фиктивный checkpoint ради самого перехода.

Если durable запись невозможна, явно укажи это в handoff.

---

## 8. Проверка перед выдачей handoff

Перед финализацией проверь:

- нет ли противоречий между разделами;
- совпадает ли Exact resume point с Remaining work;
- не объявлена ли незавершённая задача закрытой;
- не перепутаны ли research evidence и runtime implementation;
- не перепутаны ли local test PASS и production/release PASS;
- указана ли необходимость fresh проверки внешнего состояния;
- сохранены ли важные запреты и owner boundaries.

---

## 9. Формат результата

По запросу пользователя:

`Подготовь переход в новый чат`

выдай:

1. короткое сообщение о том, что handoff подготовлен;
2. один цельный блок `NEW CHAT HANDOFF`;
3. при возможности — отдельный текстовый файл с тем же содержимым;
4. точную инструкцию пользователю: вставить/загрузить этот handoff в новый чат и написать `Продолжай с указанной точки`.

Не разбивай handoff на несколько независимых сообщений, если в этом нет необходимости.

---

## 10. Поведение нового чата

Если новый чат получает такой handoff, он должен:

1. прочитать его полностью;
2. определить authoritative sources;
3. выполнить минимальную fresh state/TOCTOU-проверку;
4. устранить расхождения между handoff и текущим состоянием;
5. не повторять завершённую работу;
6. продолжить с `Exact resume point`;
7. периодически создавать новый handoff по тому же правилу по запросу пользователя.

Главный принцип:

**Новый чат должен продолжать проект, а не заново реконструировать его историю. Handoff хранит рабочую модель состояния, а изменяемый source of truth подтверждает, что эта модель всё ещё актуальна.**

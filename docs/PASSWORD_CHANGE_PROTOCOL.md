# Протокол смены пароля

Статус: **реализовано** (решение пользователя 2026-09-23, `OPEN_QUESTIONS.md` §4 п.2,
`CRYPTOGRAPHY.md` §12): `ProtectedStoragePasswordChangeService` (§4, §5; перешифровка —
`IKeyedSqliteConnectionFactory.Rekey` → `sqlite3_rekey`), разбор прерванной смены встроен в
`ProtectedStorageCredentialService.UnlockOrInitializeAsync`, «Настройки» → «Сменить пароль…»
(`JournalWindow.PasswordChange.cs`). Путь смены на production SQLCipher 4.17.0 проверяет smoke-хост:
Native run `35857482543` на `763308a` — SUCCESS (Build run `35857480052` — SUCCESS). Ревизия §5
(недописанные копии, копии потерянной базы): `6718a03`, `7bcc6d0` — Build run `35869608153` и Native
run `35869612180` на `7bcc6d0` — SUCCESS. Ручной smoke на Windows — `UNVERIFIED`.

## 1. Что меняется

Новый MasterKey = Argon2id(новый пароль, **та же** соль хранилища). Соль, `StorageId`, заголовки
файлов и содержимое баз не меняются; меняется ключ, которым зашифрована каждая база. Отдельного файла
ключа нет, поэтому перешифровываются **все** базы хранилища:

- `Current/current.db`, `Current/storage-catalog.db`, каждый `Archive/archive_*.db`
  (`StorageDatabaseFiles`).

Копии в `Current/CatalogQuarantine` не перешифровываются, а **удаляются** при переключении: это
диагностические копии заменённых (часто повреждённых, то есть вообще не открывающихся) Catalog, и
иначе они остались бы читаемыми старым паролем.

Внешние файлы (`Files/`, `Trash/`) не шифруются MasterKey и не затрагиваются.

## 2. Инварианты

1. **Всегда есть пароль, открывающий всё хранилище.** В любой момент, включая сбой, каждая база
   либо открывается старым ключом, либо новым, и по файлам однозначно видно, какой пароль нужен.
2. **Отдельного marker'а нет.** Состояние прерванной смены восстанавливается только по файлам баз
   (решение «достаточно файлов баз и пароля», `CRYPTOGRAPHY.md` §3).
3. **Точка фиксации — полный набор проверенных копий.** Пока хоть у одной базы нет проверенной
   копии с новым ключом, смена считается несостоявшейся, и её откат — удаление копий.
4. **Оригинал заменяется только проверенной копией**, атомарным переименованием с заменой.

## 3. Запуск (App)

«Настройки» → «Сменить пароль…», Clipensk разблокирован:

1. Пользователь вводит текущий пароль, новый пароль дважды и (необязательно) новую подсказку.
   Текущий пароль проверяется выводом ключа по соли хранилища и сравнением с ключом сессии
   (постоянное время); неверный — отказ, ничего не меняется.
2. Clipensk блокируется сам, как при переносе хранилища (`DATA_ROOT_RELOCATION_PROTOCOL.md`, D2);
   ключи — старый (копия ключа сессии) и новый — остаются только у операции смены. Незавершённые
   операции хранилища к этому моменту уже доведены стартовой последовательностью разблокировки;
   если их следы (staging) всё же есть — отказ с сообщением (§4).
3. Смена выполняется до сессии (§4) с прогрессом. После неё — экран разблокировки: нужен новый
   пароль.

## 4. Протокол (Storage)

Выполняется при заблокированном Clipensk, с двумя ключами хранилища (старым и новым) в памяти.

**Предусловия** (отказ до любой записи):

- в каталоге данных нет незавершённых операций: ни staging Archive Rotation/Split
  (`.clipensk-archive-rotation-*`, `.clipensk-archive-split-*` — их доводит следующая разблокировка
  текущим ключом), ни копий прерванной смены пароля (`*.clipensk-rekey`), ни журналов баз, ни
  неизвестных `.clipensk-*` (в корне, `Current`, `Archive`). Остатки операций, которые выполняются
  целиком или никак (инициализация хранилища, восстановление и замена Catalog, «Начать текущую базу
  заново», создание архива, пробная запись), после аварии ничьи: они удаляются — иначе остались бы
  читаемыми старым паролем; занятый остаток — «занято», попытка повторяется;
- каждая база из §1 открывается старым ключом (`quick_check`, `DatabaseIdentity` с тем же
  `StorageId`) — проверяется на её побайтной копии в фазе 1: пока базы удерживаются эксклюзивно,
  SQLite их не откроет; отказ удаляет копии;
- свободного места на томе хватает на копию всех баз.

**Фаза 1 — копии.** Для каждой базы `F` по порядку: побайтная копия в `F.clipensk-rekey`, открытие
копии старым ключом, `sqlite3_rekey` новым ключом с той же солью, закрытие, повторное открытие
**новым** ключом и проверка (`quick_check`, `DatabaseIdentity`, та же роль и `StorageId`),
удаление журнала копии. Оригиналы не меняются. В конце фазы набор баз перепроверяется: базу,
опубликованную операцией, которая после блокировки ещё завершалась, копия не покрывает — тогда
фаза 1 откатывается с «занято», и App повторяет попытку. Отмена или сбой в фазе 1 — копии
удаляются, пароль прежний.

**Фаза 2 — переключение.** Только после того, как у **каждой** базы есть проверенная копия:
эксклюзивные дескрипторы оригиналов освобождаются, каждая копия переименованием с заменой
становится оригиналом (`File.Move(..., overwrite: true)`) — архивы, затем Catalog; затем удаляются
копии карантина Catalog; `current.db` — последним. Отмена в фазе 2 не принимается: переключение
доводится до конца. Любой сбой до переключения `current.db` оставляет хотя бы одну копию, и
восстановление (§5) доводит всё, включая удаление карантина.

**Завершение.** Копий не осталось; подсказка к паролю в `settings.json` заменяется новой.

## 5. Восстановление после сбоя

Подбор ключа при разблокировке (`IdentifyAsync`, `CRYPTOGRAPHY.md` §4) пробует и копии
`*.clipensk-rekey`: они несут ту же соль. Если копии есть, после подбора ключа `K` (из любого пути
разблокировки — обычной, восстановления Catalog, «Начать текущую базу заново») файлы приводятся в
согласованное состояние до всего остального:

| Состояние | Что видно по файлам | Действие |
|---|---|---|
| Фаза 1 прервана, введён **старый** пароль | `K` открывает каждый оригинал | копии удаляются, разблокировка обычная |
| Фаза 1 прервана, введён **новый** пароль | `K` не открывает ни одного оригинала, и не у каждой базы есть копия, открывающаяся `K` | «пароль неверен»: смена не состоялась, действует старый; копии не трогаются |
| Все копии готовы или фаза 2 прервана, введён **новый** пароль | каждая база открывается `K` сама или через свою проверенную копию | переключение доводится до конца, разблокировка обычная |
| Фаза 2 прервана, введён **старый** пароль | часть баз уже переключена и `K` не открывается ни сама, ни через копию | отказ с сообщением: смена пароля завершена частично, нужен **новый** пароль |

Полный набор готовых копий при старом пароле, открывающем все оригиналы, — это прерванная до
переключения фаза 1: откат. Тот же набор при новом пароле — доводка: пользователь хотел сменить
пароль и вводит новый.

- Копия, недописанная при сбое (оборвалась запись или перешифровка), — просто не готовая копия:
  подбор ключа не считает её ошибку повреждением хранилища, и новый пароль при прерванной фазе 1
  получает «пароль неверен», а не «хранилище недоступно».
- Удаляются только копии, рядом с которыми лежит их база. Базу смена не удаляет, поэтому её
  отсутствие означает, что она потеряна иначе (удалена вручную, изъята антивирусом). Копия такой
  базы, которая открывается ключом `K` и проходит ту же проверку, ставится на её место: при откате
  сразу, при доводке — вместе с переключением. Любая другая копия потерянной базы может оказаться
  единственным, что от неё осталось, и не удаляется.
- Если потерян `current.db`, а его копию `K` не открывает, откат не удаляет **ни одной** копии: она
  может быть под другим паролем, и только вместе с остальными копиями тот доведёт смену и вернёт
  `current.db` на место. Без `current.db` сессия не начинается, поэтому копии не устаревают, а
  порядок ввода паролей (сначала прежний, как советует сообщение о сбое смены) ничего не решает.
  Экран разблокировки объясняет, что делать: разблокировать другим паролем или, если так не
  выходит (копия недописана либо остальные копии уже удалены), удалить её вручную — её записи будут
  потеряны. «Начать текущую базу заново» при такой копии не предлагается и отказывает
  (`CURRENT_RESTART.md` §3): рядом с новым `current.db` она выглядела бы остатком и была бы удалена.

## 6. Ограничения

- Перешифровка не стирает прежние зашифрованные байты с диска надёжно: блоки заменённых файлов
  освобождаются файловой системой, но не затираются. Резервные копии хранилища, сделанные до смены,
  по-прежнему открываются старым паролем.
- Время и место растут с объёмом баз: копия каждой базы создаётся до переключения.
- Staging ротации или разделения архивов, чей marker пропал вместе с Current (после «Начать текущую
  базу заново», `CURRENT_RESTART.md` §4), некому довести, а удалять его автоматически нельзя — он
  может держать единственную копию части истории. Смена пароля на нём отказывает, пока его не
  разберут вручную. То же — с копией `*.clipensk-rekey` потерянной базы, которую не вернул на место
  ни один пароль (§5).
